## 三、容易冲突的协作边界

1. **公共样式**：`src/index.css` 按模块负责对应选择器，A 负责最终整合。不要多人整体格式化、重写或覆盖该文件。
2. **统一入口**：`src/App.tsx`、`package.json`、运行配置由 A 汇总提交；其他成员提出路由、依赖和脚本变更。
3. **算法复用**：`src/crypto/engine.ts` 由 B 维护公共算法接口，C 的图片处理、D 的通信功能调用它；避免复制出不一致的加密实现。
4. **Agent 与账户**：A 负责对话界面、流式模型调用和白名单工具；D 负责 `auth.mjs` 中账户、会话及会话记录持久化接口。涉及会话结构的变更先由 A、D 对齐。
5. **图片遥测与中继**：C 负责 `src/image-lab/telemetry.ts` 的客户端事件，D 负责 `relay.mjs` 的服务端中继；消息字段双方确认。
6. **测试归属**：每个人维护自己模块的验证材料，A 负责跨模块联调；不能把所有测试和文档都交给 C、D。
7. **代码合并**：每人使用独立功能分支；公共文件变更集中合并。账号数据、真实密钥和 `.env.local` 不作为团队交付材料传播。

## 五、PPT 与汇报安排

- **C 主做 PPT**：目录结构、视觉统一、流程图落版、截图和演示视频整理。A、B、D 各自提供自己模块的简要说明、关键截图、测试结论和限制，不能让 C 代写所有技术原理。
- **D 主做汇报**：开场、模块串联、演示节奏、总结和常见问题整理。算法追问由 B 主答，AI/架构由 A 主答，图片安全由 C 主答，通信/账户由 D 主答。
- **避免临近汇报继续加功能**：核心代码冻结后，C、D 主要投入 PPT 与排练；本模块重大问题仍由本人跟进，跨模块联调由 A 协调。
